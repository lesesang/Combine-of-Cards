# 원소 유발 자동화 구현 묶음 — 검증 전

기준 main `43b72d0` / PR #74. 사용자가 **“지금부터는 일단 자동화만 해줘. 테스트는 나중에 한 번에”**라고 변경했다. 이 작업은 구현 브랜치/draft PR에 모으며 테스트·CI 실행·main 병합·배포를 보류한다. 기존91건 효과 증거와555개 통과 기록은 PR #74의 기준선일 뿐, 이 변경의 검증 결과가 아니다. 효과 증거 보고서에 미검증 구현을 새 증거로 등록하지 않는다.

누적 draft PR: [#75](https://github.com/lesesang/Combine-of-Cards/pull/75), 브랜치 `feat/elemental-trigger-automation`. 이번 후속은 원소 유발2종과 일체화 조건2종을 추가한다.

`src/triggered-effects.mjs`가 다섯 유발을 명시적으로 등록한다. `pendingMonsterTriggers`에 선언 순서와 효과 스냅샷을 JSON으로 보관하고 후발부터 하나씩 기존 `abilityResponse`에 연결한다. 윈드 걸은 다섯 몬스터 유발과 그 카운터에 대응하며, 주문/일체화/소환으로 범위를 넓히지 않는다. 기존 비용/횟수 예외도 바꾸지 않는다.

랜드 체류는 테라와 같은 `dragonResidence` 기록을 사용한다. 필드 조종권 이동은 유지하고 영역 이탈은 초기화한다. 두 번째 시작에 무효 상태였다면 그 체류의 기회를 나중에 다시 발생시키지 않는다. 선언 후 무효화되어도 그 체류의 교환을 재시도하지 않는다. `pendingTurnStart`로 기존 턴 시작 후속 처리와 정상 드로우를 유발 해결 뒤까지 기다리게 한다.

인피니티는 상대의 패 내용을 선택 UI/로그로 공개하지 않고 서버에서 무작위로 고른다. 덱 위 카드는 순서대로 처리하며 부족하면 존재하는 수만 제외한다. 묘지 선택은 상대 플레이어 권한으로 `infinityGraveChoice`에 연결한다. 선택 중 일반 행동/패 열람/진화 비용 열람을 잠그고 UID 중복/영역/요구 수량을 검사한다. 하·중·상 AI의 자기 묘지 선택과 사람의 대응 대기를 연결한다. 승패/항복 시 대기 상태를 정리한다.

## 개발자 판단과 남은 통합

- 워터는 공격 대상으로 지정되면 자동 선언하고 그 순간 횟수를 사용한다. 공격력 부등식은 해결 시 검사한다. 재선택된 워터도 대상 선언으로 취급하지만 인피니티의 공격 선언 효과는 재선택만으로 다시 발생시키지 않는다.
- 인피니티의 ‘최대2장’은 각 영역에 존재하는 수와2 중 작은 수만큼 처리한다. 묘지 선택을0장으로 임의 회피하는 선택은 제공하지 않는다. 필드/일체화는 제외하지 않는다.
- 랜드의 교환은 변경 가능한 ATK/HP 층에서 수행하고 독립 마검 배율은 유지한다. 예를 들어 변경 가능한ATK100·HP230·독립×2이면 교환 뒤 ATK층230·HP100이며 표시ATK460이다. 이는 기존 매치 계열의 능력치 설정과 일관된 **개발자 해석**이며 사용자 개별 확정으로 주장하지 않는다. 마검의 기간/지불/중첩 재정은 그대로다.
- 랜드 유발을 기존 드로우 시점 자동 처리보다 먼저 해결하도록 후속 처리를 보관했다. 다른 모든 턴 시작/파괴 유발까지 하나의 동시 사건 그룹으로 통합한 것은 아니다.
- 새 유발들은 원소1번 교체와 공용 제한을 공유하지 않는다. 원소 교체를 임의 체인 중 추가하는 범용 후발 삽입은 계속 남는다.
- 이번 코드는 실행 검증하지 않았다. HTTP 복구/동시 유발/카운터/비공개/AI/승패·후속 처리의 실제 정상 동작과 기존 회귀 영향은 후속 일괄 검증에서 확인해야 한다.

후속으로 [진화·소환 연계19종과 일반 소환 대응](EVOLVED_AND_SUMMON_AUTOMATION_DRAFT.md)을 작성했다. 다음은 묘지 이동 발동·복사·장착과 공통 파괴/턴 시작 유발 통합이다. 사용자 개인 Cloudflare D1을 위해 상태는 JSON 자료만 사용하되 실제 D1 연결과 운영 배포는 여전히 하지 않았다.

## 후속: 추가 공격2종과 파괴 사건 대기

기존 `grantElementalBattleAttack` 즉시 부여를 제거하고 동일한 원문 조건을 `recordElementalBattle`/`recordMonsterDestruction` → `deferredMonsterTriggers` → `abilityResponse`로 옮겼다. 추가 공격을 얻기 전에 상대가 윈드 걸로 무효화할 수 있으며 무효화되어도 UID/효과2의 그 턴 사용은 반환하지 않는다. 기본 자기 턴1회, 원소1번 공유 제한과 분리, 다른 물리 카드의 독립 사용, 기존 추가 공격과 합산을 유지한다.

플레임은 전투 피해 직전의 두 실제ATK(마검 배율 포함)를 스냅샷한다. 직접 공격은 제외하고 피해 면역인 몬스터와의 전투도 비교한다. 대상이 이미 파괴되었어도 전투 당시의 조건으로 선언한다. 볼케이노는 공통 파괴 처리에서 살아 있는 필드 소스 UID와 피해자 조종자/몬스터 여부를 검사한다. 비용 파괴·자기 몬스터 파괴·패 버리기·단순 묘지 이동·원인 불명 파괴는 추가 공격의 근거로 삼지 않는다. 파괴 직후 부활한 피해자도 파괴 사건 자체는 유지한다. 여러 동시 처치는 물리 카드/효과2/턴별 한 번만 대기시킨다.

발생 사건의 소스 체류 세대·턴·조종자를 JSON으로 보관한다. 현재 주문/소환/필드 체인과 선택·기존 첫 파괴 회복의 순서 처리가 끝난 뒤 새 대응을 연다. 하위 유발이 남은 현재 그룹에는 임의로 끼워 넣지 않는다. 해결 때 소스 이탈·재진입·조종권 변경·무효 상태를 다시 검사하며, 종료된 대전에는 공격권을 부여하지 않는다. 이는 **새 유발을 현재 체인 완료 후 선언하는 개발자 처리 정책**이다. 모든 종류의 동시 파괴 유발을 하나의 그룹으로 합쳤다는 뜻은 아니다.

마검 처치별 다음 자기 턴 배율 적립은 기존 `recordSwordKill`에 독립적으로 남겨 둔다. 볼케이노의 기본1회 제한을 마검에 적용하지 않는다. 원인 UID를 전달하는 파괴 경로를 연결한 것이며, 아직 없는 복사/부여 효과나 모든 특수 카드의 처치 귀속을 구현했다는 뜻은 아니다.

## 후속: 일체화 사용 조건2종

`src/integration-history.mjs`의 실제 사건 기록을 `planActivation`에 연결하여 사람과 AI가 같은 조건을 검사한다. 기존에는 두 조건의 사전검사가 없었다. 이제 조건이 없어서 사용 가능한 일체화만 고르던 AI 후보 필터도 두 카드에 한해 확장한다. 대전 화면에는 자기 덱의 조건 진척을 표시한다.

- **프람덴베르카 COC-10-005:** 디트리히001·프란츠003·율리우스004가 각각 필드에서 파괴되어야 한다. 원래 소유자의 게임 이력으로 세 종류를 기록한다. 같은 종류를 반복 파괴해도 다른 종류를 대체하지 않는다. 전투·효과·실제로 지불된 파괴 비용은 인정하고, 패 파괴/버리기·릴리스·소재 이동은 인정하지 않는다. 부활해도 이미 발생한 사망 기록은 지우지 않는다. 조종권을 빼앗긴 자기 카드의 죽음은 원래 소유자에게 귀속하는 **개발자 해석**이다.
- **슈 COC-31-004:** 상대 몬스터 필드가 연속3개의 완전한 게임 턴 동안 비어 있어야 한다. 양쪽의 턴을 각각1턴으로 세며 일체화 칸은 제외한다. 토큰과 HP를 가진 몬스터화 카드도 필드 점유로 취급한다. 중간에 잠깐 소환했다 바로 사라져도 그 턴과 연속 기록은 끊긴다. 소환 무효로 필드에 실제 진입하지 않은 카드는 기록을 끊지 않는다. 이는 빈 필드 제압을 보상하는 덱 흐름을 살린 **개발자 해석**으로, 사용자의 개별 확정이라고 표기하지 않는다.

두 기록은 로그500개 제한과 독립적으로 JSON에 보존한다. 구 저장에 기록이 없으면 과거를 묘지/로그에서 추측하지 않는다. 슈는 이미 시작된 미관측 턴을 완전한 빈 턴으로 세지 않고 다음 실제 턴 시작부터, 배회자는 이후 실제 파괴부터 기록한다. 기존 대전에서 이전 조건 달성이 자동 복구되지는 않는 제한이 있다.

## 일괄 검증 때 반드시 다룰 항목

테스트 파일·CI 워크플로는 변경하거나 실행하지 않았다. 기존 원소 전투 테스트의 ‘방어 직후 즉시 추가 공격’ 기대는 새 대응 후 해결 흐름에 맞춰 정당하게 갱신해야 한다. 추가 공격 무효/중첩/재소환/다중 처치, 기존 첫 파괴 회복과 동시 처리, 일체화2종 실패 시 무비용·AI 선택·원소유권·짧은 필드 진입·구 저장/재시작·HTTP 권한/버전/UI를 한 번에 검증해야 한다. 현재 기준선의 성공 수치를 새 구현의 증거로 인용하지 않는다.
