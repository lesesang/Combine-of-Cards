# 개인 Cloudflare D1 연결 계획

2026-10-15 사용자가 추후 자신의 Cloudflare D1에 연결하겠다고 지정했다. 운영 DB 목표는 D1이다. 현재는 Node 단일 프로세스의 `rooms.json` 저장이며, D1 연결·배포·데이터 이전은 아직 하지 않았다. 계정 ID나 비밀 토큰을 저장소에 넣지 않는다.

## 설계 기준

- 카드 효과 모듈에는 SQL이나 Cloudflare binding을 넣지 않는다. 게임 상태는 JSON 가능 객체로 유지하고 저장·HTTP 계층에서 영속화를 처리한다. 현재 소유권, 실물 UID, 독립 효과 횟수, 비용 지불 후의 대응 스택과 비공개 선택도 같은 스냅샷에 포함된다.
- 다음 저장소 PR에서 비동기 RoomRepository 경계를 분리한다: create, load, commit(code, expectedVersion, nextSnapshot, actionId). 로컬 파일 구현으로 기존 회귀를 유지한 뒤 D1 구현을 추가한다. 현재 동기 save()를 D1 호출로 단순 치환하면 요청 간 경쟁·실패 롤백이 깨진다.
- D1에서는 방별 JSON 스냅샷과 version을 기본 저장 단위로 한다. `UPDATE ... WHERE code=? AND version=?` 조건부 갱신의 변경 행 수를 확인하여 충돌은409로 돌려준다. 소유권/토큰 검증은 서버에서 하고, 비공개 원본 스냅샷은 브라우저에 직접 반환하지 않는다.
- 룸 변경과 actionId 중복 방지는 동일한 원자적 커밋으로 처리한다. D1 batch의 트랜잭션 특성 및 조건부 갱신 실패(0행)는 SQL 오류가 아니라는 점을 고려해야 한다. 성공 여부와 무관하게 별도 액션 로그가 기록되는 설계는 금지한다. 실제 어댑터 작성 시 공식 D1 문서로 지원 API/제한을 다시 확인한다.
- 데이터에는 schemaVersion, rulesVersion, balanceRevision, catalogDigest를 구분해 저장한다. 현재 publicState의 balanceRevision은 실행 서버 버전 표시일 뿐, 저장 대국의 규칙 고정을 구현한 것이 아니다. B1 전 진행 중 대국은 종료한 뒤 신규 대국으로 전환한다. 기존 방에 현행 버전을 소급 기입하여 이전 규칙을 재현한다고 주장하지 않는다.
- Workers 런타임으로 옮기면 Node의 파일 I/O·HTTP 서버·암호 API 의존을 함께 분리한다. D1만 붙인다고 현재 Node 서버가 그대로 Workers에서 실행되는 것은 아니다. 외부 Node 호스트를 유지할 경우 D1 접근 경로·자격증명·지연을 별도 검증한다.

## 이전 순서와 인수 기준 (#29)

1. 저장소 인터페이스와 로컬 어댑터를 별도 브랜치/PR로 분리하고 기존 JSON/HTTP 원자성 회귀를 통과한다.
2. 로컬 D1 마이그레이션과 어댑터를 만들고 신규 방·참가·대응 대기 중 복구·AI 행동·동시 요청·중복 액션·저장 실패를 검증한다. 배포 binding은 사용자의 실제 D1 준비 시 설정한다.
3. 기존 파일 백업 → 스키마 버전 확인 → 멱등 가져오기 → 방 수·UID·상태 해시 대조 → 읽기 검증 → 쓰기 전환. 원본 파일은 검증 완료 전 삭제하지 않는다.
4. 최종 PR의 Node tests / Verify TCG beta와 D1 통합 검사를 통과하고, 운영에서 신규 대국·재접속·비공개 정보·충돌·복구를 확인한 뒤 배포 완료를 기록한다. 아직 이 기준을 완료하지 않았다.
